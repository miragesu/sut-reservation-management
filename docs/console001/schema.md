# Proposed SQLAlchemy schema and Alembic plan

Design only: no model or revision file is added. Use existing Base naming convention, integer entity PKs, UTCDateTime (aware UTC Python / naive UTC SQLite), FK RESTRICT/no destructive ORM cascades, explicit enums/check constraints and indexed foreign keys. Opaque UUIDs below are public handles, never authorization. Reuse existing users, labs, suts, current_usages, login_sessions and audit_events. No changes to reservation timing or usage ownership.

If durable staging is later required, review a new encrypted-staging design rather than inserting candidate secrets into JSON or tickets.

## Integrity and transaction rules

- `BEGIN IMMEDIATE` before quota count/allocation, unique-pair claim, grant creation/extension/expiry, ticket redemption or endpoint mutation. Never hold this lock during SSH exchange, crypto RPC or WebSocket lifetime; use short context-managed SQLAlchemy sessions in thread workers, not a synchronous Session across await.
- Quota: count slot_held=1 for user, reject >=10, allocate in the same transaction. CAS reconnect increments generation on the same row without adding another slot. Startup retires stale boot IDs before admissions; lost-tab leases release slots. No unique-per-user-SUT restriction and no writer lease table.
- Cross-table Lab rule: planned SQLite INSERT/UPDATE triggers validate mapping's Client.lab_id equals SUT.lab_id whenever configured, including retained bindings; Client Lab update rejects incompatible bindings even disabled/archived; SUT Lab update likewise. Service supplies actionable conflict lists. Existing SUT Lab immutability remains. Adding Clients also requires Lab deletion to reject any Client references, including disabled records, preserving history.
- `binding_active` is a mapping state, not the Client enabled flag. Client disable retains bindings and their slot; archived/deactivated bindings release active uniqueness. Clearing retains immutable history. Proposed archive hook sets binding inactive and revokes sessions atomically; restore must revalidate uniqueness and cannot steal a slot or silently attach to reassigned hardware. See H2 in compatibility for explicit review.
- Expired grants cannot be represented by a clock-dependent partial index. Under write serialization mark due active grant expired before insert; validity always tests exact timestamps and operational state, even before sweeper catches up. Grant-extension CAS and expiry race resolve at server time; old expired grant is never extended/reanimated.
- Client network/credential updates use short-lived broker success proof bound to Client/version/IP/port/username/method/host key/candidate digest. Preflight checks do not reserve uniqueness forever; recheck unique IP/name, trust, actor and confirmed affected set at commit. New Client uses transient UUID for encryption AAD before assigning integer ID; circular credential FK resolves inside one transaction, never a visible half-created enabled Client.
- Database uniqueness rejects concurrent collisions, translated to 409. Metadata audits, revision, revocation outbox and entity epoch changes commit together. Audit failure rolls back security mutation; no silent success without audit. Lifecycle failure closes attachment safely even if audit DB unavailable, with bounded metadata-only retry.

## Existing BMC inventory compatibility

Keep `suts.bmc_ip` and `host_ip` unchanged, including existing IPv6/blank values and admin inventory APIs. New RD-managed console_bmc_endpoints is the sole direct-SSH target; do not auto-copy inventory to an executable endpoint, trust a key or initiate a probe on migration. UI labels inventory versus Console target explicitly and offers deliberate copy/edit with normal version/history rules. This avoids widening existing admin SUT mass-assignment permissions or dropping old IPv6 data. Same BMC IPv4 across distinct SUTs is not forbidden by owner decisions; warn about potential duplicate physical target but do not invent a uniqueness prohibition. Trust is still SUT/target/version scoped.

## Planned migration and recovery

Proposed next revision `console001_foundation` with down_revision=`c2026101601` (rebase/recheck head when Phase B starts; revision name not reserved or implemented here).

1. Isolated test copies first: empty database, existing latest-main fixture with users, sessions, both Labs, usages, queues, all reservation states and archives; also upgrade an older supported revision through the existing chain.
2. Cold backup old database plus WAL/SHM as appropriate, configuration and image digest; never copy a live file casually. Inventory schema/row counts, FK check and integrity check before migration.
3. Add only new Console tables/indexes/triggers. Do not rebuild/drop existing coordination tables or backfill actionable targets/credentials. New tables empty; feature OFF; login IDs, hashes, usages/history and existing timings unchanged. Verify head, schema comparison, counts and a deterministic digest of preexisting rows.
4. Rotation and cryptography initialize only after operator separately supplies keyring; migrations do not generate roots, decrypt data or contact network. A database with no Console credentials must boot in OFF mode without a key.
5. Rollback: disable Console and stop services, preserve new writes and encrypted-secret backup, restore matching pre-upgrade backup/config/image into an isolated empty directory, validate, then separately authorize production recovery. Proposed downgrade refuses destructive drops once Console data exists; do not assume old code tolerates added triggers/FKs. No automatic data deletion or backwards secret conversion.

Migration SQL, triggers, concurrency tests, keyring provisioning and runtime cleanup are Phase B work and remain unimplemented. Tests must prove no network during upgrade and no credential/ciphertext in revision/audit payloads.
