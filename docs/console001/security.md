# Security design and residual risks

All controls below are proposed, except the explicitly referenced owner policies. No control has been deployed by Phase A. Read [compatibility](compatibility.md) for review blockers, including ambiguous public-target wording.

## Threat model

Assets: login cookies, Client SSH secrets, direct BMC credentials, trusted keys, mappings, terminal input/output, coordination SQLite and remote tmux/minicom availability. Actors include malicious/compromised RD, LAN interceptor, hostile SSH server/terminal output, compromised Client, operator error and process crash. Admin and RD are authenticated but not inherently safe infrastructure operators. A compromised gateway/host with key access remains a high-impact trust failure.

| Threat | Required mitigation / remaining risk |
|---|---|
| RD targets non-BMC service through gateway (Q5) | Canonical IPv4 only; no DNS/IPv6/URL/userinfo, integer/octal/hex alternate encodings; deny special/self destinations at save AND immediately before every TCP dial, including candidate auth/key probe; broker independent checks and host egress firewall. No Lab CIDR allowlist. Allowed address can still run non-BMC SSH; SSH/banner is not BMC attestation. |
| LAN interception/injection (HTTP exception) | Explicit two opt-ins, exact Origin, CSRF, ticket and LAN restriction reduce accidental/cross-site exposure but DO NOT stop LAN MITM or sniffing. Cookies/passwords/terminal stream remain readable and modifiable. SSH protects only gateway-to-target. |
| Malicious RD accepts attacker's key (Q6/Q7) | Explicit trusted-source comparison, old/new fingerprint and impacted users, atomic trust audit and revocation. No TOFU auto-accept. RD retains this confirmed authority; audit cannot prove comparison or repair false trust. Client trust has cross-SUT blast radius. |
| Stored credential theft (Q9/Q69) | Independent AEAD root, separate broker mount, non-reveal replacement-only API, redacted errors and backup separation. Runtime broker/host compromise can decrypt; database encryption does not solve transport compromise. |
| Cross-site WebSocket hijacking | Exact scheme/host/port Origin allowlist derived from reviewed external origin, no wildcard/null/missing Origin; login + CSRF-issued ticket + one-use redemption + same login/tab binding. SameSite cookie alone insufficient. |
| Stale session types into changed endpoint | Versioned admission fence, durable revocation, per-input broker authorization, deny reconnect after invalidation; bytes already delivered cannot be recalled. |
| tmux escape or shell injection | Restricted helper and exact identifiers, no raw exec command from UI, no generic SSH shell on Client, deny forwarding/subsystems. Native attach is insufficient; helper proof blocks Phase C. Direct BMC interactive shell is an explicit feature and cannot prevent user-entered shell commands from pivoting on the BMC itself. |
| Shared writer collision (Q15) | Shared notice, distinct RD list/mode; bounded byte ordering per connection. No exclusive writer lock or latest-typist tracking. Concurrent writes may corrupt commands; accepted collaboration risk. |
| Resource exhaustion / password brute force | Fixed ten slots/user, bounded pending probes/challenges, one in-flight attempt/flow, max three BMC attempts/flow, transport byte/frame budgets and backpressure. No extra failed-password rolling lockout; remote BMC may lock account independently. |
| Terminal escape output/XSS/clipboard abuse | Maintained local xterm.js with narrowly selected addons; no output as HTML, no OSC52 automatic clipboard, no file/image download/recording/link auto-open handlers. Escape all metadata. Read-only drops automatic emulator replies as input. |

## IPv4 and egress enforcement

Positive syntax validation is not sufficient. Explicit versioned deny categories: 0/8 unspecified/current-network, 127/8 loopback, 169.254/16 link-local/metadata, multicast 224/4, reserved 240/4, limited broadcast, network/broadcast of actual directly attached subnets, documentation/benchmark/protocol-assignment ranges not valid as real BMC targets, and deployment-specific infrastructure/self addresses. Maintain a tested IANA special-purpose classification rather than relying on a Python `is_private` shortcut (which would reject legitimate intranet BMCs). RFC1918 itself is not prohibited. Include Docker gateway/bridge/container IPs, host LAN interfaces, management/control services, metadata endpoints even when nonstandard, DB/admin endpoints and SSH broker/gateway addresses in the self/infrastructure deny inventory. Account for Docker DNAT, host routes and translated self-targets at host firewall; app IP comparison alone cannot see every NAT path.

No user-selected port for BMC (22 only); Client SSH port admin-configured 1..65535 but still subject to special/self deny and actual SSH key exchange. Do not probe HTTP, scan ranges, follow redirects or fall back to another target. Direct fixed-IP connect removes DNS rebinding, not routing/NAT attacks. Denied target errors are generic; do not expose sensitive infrastructure list. Save validates without reachability; denied probe/auth attempt does not send credentials. Operator gate must demonstrate egress denies, not merely document firewall intent. Public unicast destination interpretation remains D1; do not silently turn Q5 into an RFC1918 or Lab allowlist.

## Client encryption, rotation and recovery

Propose cryptography AES-256-GCM with independent 32-byte random keyring, random unique 96-bit nonce per encryption, authenticated AAD binding immutable Client public_id, credential UUID, generation, method and format version. Store key_id, nonce and ciphertext/tag in SQLite, never root keys. Root key is NOT SECRET_KEY, not an account password, not baked into an image or Compose environment value. Broker receives a read-only operator-provisioned secret file outside `/app/data`, least-readable UID10001, private parent directory; neither gateway nor database backup mounts it. A compromised app can invoke authorized broker operations but cannot request decrypt/reveal RPC.

Password and private key (optional encrypted-key passphrase in same AEAD payload) are replacement-only fields; username/method/configured status are safe metadata. Admin-provided keys are validated for supported format/algorithm; reject unsupported/hardware-agent keys in the first implementation, do not silently downgrade. Do not generate or install a remote authorized_key automatically. Keys preferred; password deployments retained. Password/key file inputs, errors, SSH library debug, reverse-proxy body capture, tracing/APM and crash/core dumps must not retain secrets; disable them for broker/Console paths. Direct BMC username/password use only per-attempt memory, no browser storage, URLs, SQLite, tickets, audit, retries or logs. Python memory cannot guarantee erasure of immutable strings: minimize lifetime, remove references promptly, avoid swapping/core dumps where feasible, never claim assured zeroization.

For Q70–72: hold candidate encrypted only in bounded broker memory, verify pinned key before authentication, authenticate with no shell/exec/tmux, issue short-lived version-bound success proof, and atomically commit only after fresh confirmation and uniqueness/permission recheck. Failed auth/IP update retains old credential/target and links; new Client failure creates no persistent Client/credential. Candidate/proof expires on cancel, timeout, logout or restart. Trust replacement independently revokes under Q74 even if a subsequent credential test fails; UI must distinguish the two separate operations instead of promising that a failed credential save undoes a committed trust replacement.

Key rotation runbook (future, not executed): take recoverable encrypted DB backup; stage new key ID alongside old; new writes use new key; re-encrypt each row using old-key decrypt/new-key encrypt with fresh nonce and CAS current ciphertext/version; verify every tag; checkpoint metadata without plaintext; concurrent credential replacement wins CAS and is retried safely. Rewrapping alone does not rotate remote SSH credentials or disconnect users. Retain old root keys for all retained backups, or re-encrypt backups under a separately tested procedure before retirement. Losing a root requires replacing Client credentials; losing SECRET_KEY alone invalidates app cookies but must not destroy stored SSH secrets. Emergency root compromise: disable Console, revoke all attachments, replace remote credentials through separately authorized operator actions, rotate keyring and assess backups; rewrapping stolen secrets is insufficient.

Back up encrypted SQLite/config/image manifest and keyring in separately access-controlled offline stores, with key IDs, format versions and matching restore inventory. Never place keyring in the same tar archive as SQLite or in Git. Cold restore to isolated storage, supply matching keyring, verify integrity/FKs/decryption of synthetic canary, then validate current host keys before actual use. Do not revive saved session slots, tickets, grants beyond their original deadlines or stale trust without endpoint/version checks. Root/key ID missing, tag failure or malformed ciphertext fails Console closed without plaintext fallback; coordination remains usable when Console explicitly disabled. Disaster exercise must test old backup after key rotation.

## Host trust and SSH restrictions

Probe retrieves algorithm/public key and SHA256 fingerprint with no password/key signing before trust. Unknown/changed response is not authorization. Challenge binds user/login, exact target/version and candidate key, expires proposed 60s, and displays old/new values, trusted-source instruction and affected counts. Initial Client acceptance is creating admin only (Q73); later active RD can update Client/BMC trust (Q6/Q7) without Claim. Do not inherit gateway system known_hosts, auto-add keys, ignore mismatches or use known_hosts=None. Prototype actual library key-exchange/auth ordering and pin the complete key, not just a UI string. If key changes again between probe and authentication, abort with a fresh challenge before any credential transmission.

Client trust change revokes every Client UART attachment; BMC trust change revokes that SUT's BMC only. Client IP/port change requires new endpoint trust proof with no silent carryover. Trust/audit/version/revocation atomic; successful replacement cannot leave old streams writable. New connections manually reconnect. No agent forwarding, remote/local/reverse TCP forwarding, tun, X11, SFTP/SCP, arbitrary Client exec or credential export. Broker policy survives untrusted client JSON. Remote Client account must be pre-provisioned to the restricted helper/socket only; web gateway must not install helper, change socket permissions or run sudo. Direct BMC user credentials retain whatever remote permissions that BMC grants; no promise to prevent a remote shell's own network operations or power commands typed by the user. The app supplies no BMC power UI, automated firmware action or power-command API.

## HTTP/WS operator exception and future TLS

`CONSOLE_ENABLED=false`, `CONSOLE_ACCESS_POLICY=claim_only`, `CONSOLE_ALLOW_INSECURE_HTTP=false` defaults; strict true/false flags and policy enum, invalid values fail startup. Settings change through Compose plus recreate, not rebuild; disable/recreate closes links, never tmux. Do not add these settings to actual Compose in Phase A.

HTTP Console requires both flags true plus explicit operator acknowledgement in future deployment guide/setup, visible plaintext-transport warning before credentials/terminal use, LAN-specific APP_BIND and host firewall/VLAN restrictions to trusted clients, no Internet exposure/tunnel and no permissive reverse proxy. Existing HTTP login requires COOKIE_SECURE=false; do not silently weaken it from Console flag. Require explicit coherent configuration for HTTP, and COOKIE_SECURE=true with HTTPS. Cookie remains signed HttpOnly SameSite=Lax, no secret in cookie. Capture-free proxy/application logging, no-store responses, exact Origin (http for ws; https for wss), CSRF and tickets remain mandatory; they do not make plaintext safe.

HTTPS uses same HTTP API semantics with TLS and wss; derive WS scheme from the verified external origin, reject mixed-content/downgrade, trust Forwarded/X-Forwarded-* only from configured trusted proxy addresses, not arbitrary request headers. Planned CSP connect-src explicitly allows only that same origin's WS scheme; preserve frame denial, no inline/eval/CDN terminal code and add WS-specific origin checks because HTTP middleware does not protect upgrades automatically. Validate no redirect to login during WS upgrade and no credentials in redirects/access URLs. Clipboard API on HTTP may fail: right-click attempts only after gesture, with Ctrl+V fallback and multiline confirmation; do not demand HTTPS-only and omit the approved exception. HTTPS/WSS must be tested separately before claiming compatible.

## Technical references (design support, not product authority)

- [AsyncSSH API](https://asyncssh.readthedocs.io/en/latest/api.html): candidate implementation supports explicit host-key validation; disabling known-host checks is unsafe. Phase C must verify its callback/auth ordering in fixtures.
- [tmux manual](https://man.openbsd.org/tmux): attachment/read-only and no-start-server options require an existing socket; native attach permissions alone are not a confinement mechanism. This motivates the helper prototype gate.
- [cryptography AEAD API](https://cryptography.io/en/stable/hazmat/primitives/aead/): proposed AEAD implementation must enforce nonce uniqueness and authenticated context.
- [xterm.js security guide](https://xtermjs.org/docs/guides/security/): treat terminal data and connected endpoints as untrusted; review addons and browser integration.

References checked 2026-11-05. Exact supported dependency versions and helper tmux versions remain Phase B/C compatibility decisions, pinned only after tests; no new dependency is installed here.
